# Restore tenant registration from Selfie

## What is happening

Before this repair, the form at `/admin/selfie` sent `POST /company-registration` to Next.js, which relayed the request to Django. The live browser returned `404` for `POST` but `405` for `GET` on that frontend URL. The deployed Django container resolves `/api/v1/superadmin/tenants/register/`, and the frontend container receives `200` for an internal `OPTIONS` request to it.

These results prove that the frontend route exists and the containers can communicate. The failed POST returned `application/json` with `{"detail":"Not found."}` and response header `x-request-id: 3e192ace-4d08-47b8-a0bd-dd62fc209210`. The old Next.js relay passed JSON responses from its upstream through unchanged, so this is consistent with an upstream API 404. It is not proof of which upstream answered: the relay selected its first configured API URL, and the response request ID is not in the hyphenated UUID format that relay generated. The matching frontend and gateway logs are needed to identify the exact hop. The relay is no longer needed for the Selfie flow.

The registration code already creates the company, tenant domain and schema, principal admin, trial dates, and welcome email. The intended repair is to restore this existing flow from Selfie, not introduce a second provisioning implementation or reopen anonymous signup.

## Findings from the repository

- Selfie now submits directly to `/api/v1/superadmin/tenants/register/` using the platform access token. It refreshes an expired token once and looks up registration status after an uncertain network failure.
- The old `/company-registration` frontend relay and the unused `/api/public/core/companies/register` relay have been removed.
- Django declares `/api/v1/superadmin/tenants/register/` and its status endpoint. The dashboard-only view requires an active public-schema superadmin or a support operator with tenant-registration permission.
- Nginx sends ordinary paths such as `/company-registration` to Next.js and `/api/` paths to Django. The checked-in exact `404` rule targets `/api/v1/core/auth/register/`, not the new Superadmin route. The running Nginx configuration still needs checking.
- The old Django `/api/v1/core/companies/register/` URL mapping has been removed. The protected Superadmin route still uses the established company/tenant provisioning implementation.
- The frontend deployment builds from `~/netily_frontend` on `prod-frontend`; the backend deployment uses its own repository and compose configuration. A successful build does not establish that both running containers contain matching route versions.

## Verify the repaired path

Run these read-only checks on the VPS. Do not submit a real company during diagnosis.

1. In the browser Network tab, confirm Selfie now sends `POST https://api.netily.co.ke/api/v1/superadmin/tenants/register/`. If it still sends `/company-registration`, the browser is running the old frontend bundle. Do not copy cookies, tokens, or the submitted password into a report.
2. Check the running frontend and backend revisions, not just the local files:

   ```bash
   cd ~/netily_frontend && git log -1 --oneline
   cd ~/netily_cloud && git log -1 --oneline
   docker inspect netily_frontend netily_backend --format '{{.Name}} {{.State.Status}} {{.State.StartedAt}}'
   docker exec netily_frontend printenv API_INTERNAL_URL
   ```

3. Prove that Django resolves the intended route in the running backend:

   ```bash
   docker exec netily_backend python manage.py shell -c "from django.urls import resolve; print(resolve('/api/v1/superadmin/tenants/register/').view_name)"
   ```

   Expected: `superadmin:tenant-register`. A `Resolver404` means the deployed backend is missing the route or is using a different URL configuration.

4. Check that the frontend can reach Django over the Docker network:

   ```bash
   docker exec netily_frontend node -e "fetch('http://web:8000/api/v1/superadmin/tenants/register/', {method:'OPTIONS'}).then(r=>console.log('HTTP',r.status,'type',r.headers.get('content-type'))).catch(e=>console.error(e.message))"
   ```

   This checks connectivity without creating a tenant. It does not establish that an authenticated `POST` succeeds.

5. If the new request fails, check backend and Nginx logs for the same time and path. For the earlier relay failure, correlate frontend/gateway logs by the browser request timestamp and path. The 32-character response request ID may be generated by a gateway, so it may not appear in the relay's own logs:

   ```bash
   docker logs --since 15m netily_backend 2>&1 | grep -E 'Company registration|tenants/register|Registration failed'
   docker logs --since 15m netily_nginx 2>&1 | grep '/api/v1/superadmin/tenants/register/'
   ```

   An anonymous request to the protected Django route should now return `401`; an authenticated operator with an empty JSON body should receive field validation errors (`400`) without creating a tenant. A `404` on the direct route points to a deployed URL/routing mismatch. A `403` means the authenticated account lacks the registration permission.

## Changes made

1. Selfie calls the protected Django API directly with a Superadmin or Support JWT and preserves validation errors.
2. The protected Django registration and status views require authentication. Registration permission remains checked against the public-schema platform account.
3. Unused frontend registration relays and the old core URL mapping are removed. The old `/core/auth/register/` block remains in place.
4. After an uncertain network failure, Selfie checks whether the tenant was created. If it cannot confirm, it asks the operator to check the tenant list before retrying.

## Acceptance checks

- An unauthenticated visitor cannot create a tenant through the frontend or Django route.
- An authenticated Superadmin can open Selfie, submit valid details once, and reach the new tenant's login page. An authorized Support operator can do the same; a Support operator without the grant receives `403`.
- The resulting company, tenant domain and schema, principal admin, trial dates, and welcome email outcome match the submitted details. A failed email does not masquerade as a failed tenant creation.
- Invalid form data yields a clear `400` with field errors, without creating a tenant. A duplicate request cannot silently create two tenants.
- A timeout can be reconciled against the resulting tenant before the form suggests retrying. The browser displays a useful request ID for unexpected failures.
- Deploy the backend before the frontend. Verify the active frontend route, backend URL resolution, and one controlled registration in production. Avoid using a production customer or payment account for that test.

## Remaining production check

The original `POST 404` was JSON `{"detail":"Not found."}`, but it still cannot be attributed to a specific upstream without the matching frontend/gateway logs. The repaired Selfie flow bypasses that relay. The work is complete only after the new direct API request succeeds for an authorized operator on production.
